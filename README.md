# 解锁限时（UnlockSessionTimer）

单机、离线、侧载使用的 Android 应用：**整机单次解锁会话的限时**。每次真正完成系统解锁后强制先选择本次使用时长（三个可编辑快捷时长 / 不限 / 自定义），计时结束调用真实系统锁屏（设备管理员 `force-lock` + `DevicePolicyManager.lockNow()`），锁屏后由家长输入系统密码解锁。不做按应用统计、每日配额、账号、云同步、VPN 或内容识别。

仅面向指定设备：OPPO R15x（PBCT10，Android 10 / API 29 / ColorOS 7.1，固件 PBCT10_11_F.23_241210，ADB 序列号 `b185de42`）。

## 设计与状态流转

统一状态机 `SessionStateMachine`（纯 Kotlin，可单测）+ 唯一执行方 `SessionController`（单线程串行，系统交互经 `ControllerEnv` 注入，可全量 JVM 测试），事件源：前台服务 `UnlockMonitorService` 动态注册的 `ACTION_SCREEN_ON/SCREEN_OFF/USER_PRESENT`、`SessionAlarmReceiver` 到期闹钟、`ReminderReceiver` 提前提醒闹钟、开机/进程恢复 `Recover` 事件、UI 选择。

| 状态 | 行为 |
|---|---|
| 已锁屏／无会话 | 无活动计时，等待真正解锁 |
| 待选择 | `TYPE_APPLICATION_OVERLAY` 全屏选择层，未选择不能进入普通应用 |
| 正在计时 | 截止时间固定，只允许查看（通知栏倒计时开关控制显示，无任何修改入口） |
| 本次不限 | 不创建到期任务与提前提醒，锁屏即结束 |
| 已发出锁屏请求 | `lockNow()` 已调用，等系统熄屏确认；10s 看门狗 + 1 次重试（均带会话标识），失败进入"锁屏失败"并记录原因 |

关键规则与实现：

- **解锁判定（R0 修复核心）**：`USER_PRESENT`（keyguard 消失）是创建会话的主入口，但**不是唯一入口**——本机 ColorOS 7.1 实测存在不发送 `USER_PRESENT` 的解锁路径，且系统可能漏发广播：设置系统密码后 keyguard 消失动画/状态翻转可能慢于广播，处理时读到 keyguard 仍锁会做**有限次数、可取消的短延迟事实复核**（300ms × 6 次，带代次；熄屏/新广播即作废旧复核）；"漏事件安全网"（亮屏未锁无会话 → 立即待选择）与**解锁一致性心跳**（亮屏期间每 2 秒核对"可交互+未锁+无会话"，服务恢复后也会主动启动）都能补出待选择。恢复检查在已解锁且能力就绪时同样直接补待选择（R6）。
- **同解锁周期防御（R4，v0.3.0 收紧）**：会话活动（计时/不限）中到达的 `USER_PRESENT` **一律视为同周期迟到/重复广播，保持会话与截止时间**，不再按"距会话开始是否超过 3 秒"猜测——事件来得晚不构成发生过真实锁屏的证据。真实锁屏周期由 `SCREEN_OFF`（结束会话）/`SCREEN_ON`（keyguard 已锁时补记结束）先行处理；会话仍活动说明本进程从未观察到锁屏周期。这样堵住"借迟到广播取消到期任务重新选择加时"的漏洞；心跳只补"无会话却已解锁"，不构成重新选择入口。
- **精确到期（R3）**：只有 `nowElapsed >= deadlineElapsed` 才锁屏；提前到达的闹钟按原截止时间重排。不存在任何"提前容差锁屏"。
- **通话熄屏区分（R5）**：到期锁屏确认（`LOCK_REQUESTED` 熄屏）优先于一切；通话中接近黑屏（AudioManager mode + keyguard 未接管 + 设备未锁定）保持会话；通话中真实锁屏（keyguard 已接管）正常结束会话。
- **计时**：`SystemClock.elapsedRealtime()` 毫秒，截止时间 = 确认时刻 + 时长；到期执行用 `AlarmManager.setExact(ELAPSED_REALTIME_WAKEUP)` + 显式广播（requestCode 1001，兼容旧版本任务）。改系统时间不影响倒计时。闹钟排定失败**如实回传状态机**（快照 `alarmScheduled=false`，通知警示），进程内每秒 tick 经同一状态机兜底触发到期。
- **旧事件失效（R1/R2）**：会话唯一自增 id；到期/提醒/锁屏结果/看门狗全部核对会话标识与开机归属；锁屏重试与看门狗带 token，会话结束即取消、执行前再次核对。接收器一律 `goAsync()`，冷启动先核对开机归属与真实锁屏状态，再消费事件。
- **冷启动恢复监控（v0.3.0）**：提醒/到期闹钟广播把进程拉起时，除处理本次事件外还会**幂等恢复监控前台服务**（仅监控开启时；闹钟广播使应用进入 Android 10 的临时允许名单，允许在该窗口启动前台服务；服务已挂载则只多一次无副作用的 `onStartCommand`）。恢复放在事件处理之后——到期锁屏由广播路径的受保护处理完成，不依赖服务启动成功，启动失败只如实记录。
- **熄屏即结束**：`SCREEN_OFF` → 结束会话 + 取消闹钟/提醒/重试/看门狗 + 清残留提醒通知；系统有安全凭据时附加 `lockNow()` 消除解锁宽限期。
- **恢复**：开机 / STICKY 重启 / 应用更新后执行恢复检查。`Settings.Global.BOOT_COUNT` 区分重启与同次开机进程恢复；重启后旧会话作废，**若此刻已解锁则直接补上待选择（R6）**；同机恢复沿用原截止时间与提醒快照，错过的提醒按 2 秒迟到窗口区分"窗口内补投一次"与"历史跳过"，已到期优先到期处理。
- **悬浮层**：可聚焦窗口，"自定义"输入在窗口内 EditText 完成；返回键不能解除选择，Home/最近任务不解除；单例防重复挂载。
- **防间接取消**：会话进行中监控开关锁定，界面/通知无停止、重置、延长、转不限入口。

## 通知与提醒（本轮新增）

| Channel | 重要性 | 用途 |
|---|---|---|
| `session` | LOW | 常驻前台服务通知；倒计时开关开启时每秒安静刷新剩余时间，关闭时只显示"正在计时"（前台化只在 attach 时执行一次 `startForeground`，此后同 ID `notify` 更新） |
| `session_reminder` | HIGH（震动、无声音） | 提前提醒 heads-up；每个时点独立通知 ID，不使用 onlyAlertOnce |
| `alert` | HIGH | 未就绪/异常提醒；就绪后自动清除 |

- **通知栏倒计时开关**（默认开）：只控制显示，不影响计时、闹钟与提醒；立即生效。
- **提前提醒**（默认开，时点默认 60/30 秒，可增删多个）：确认计时时把当时的开关与时点**快照进会话**，修改只影响下次会话；每个有效时点（`0 < 剩余秒 < 会话总时长`）只提醒一次（"还有 1 分钟将锁屏"）。广播、tick 兜底、恢复三条路径**共用同一迟到窗口（2 秒）与消费判定**；回调停顿跨过窗口的提醒记录为跳过、绝不补发过时的"一分钟/半分钟"。消费标记在通知请求前**同步落盘**（`commit()`，控制器单线程非主线程），并区分"标记已存在（重复被抑制）"与"写盘失败（保守跳过投递）"；通知请求与磁盘事务无法组成原子操作，本产品优先避免重复历史提醒，不能承诺用户一定看到了每条提醒。提醒失败不影响到期锁屏。
- **测试提醒按钮**：真实 channel 与构建路径的演示通知，独立 ID、2 秒节流、10 秒自动清除；不改状态/截止/消费标记，通知被禁用时明确提示并给出系统设置入口。
- 主界面提供系统通知设置入口，并自检应用通知总开关与提醒渠道的重要性/震动配置。

### 本轮（v0.3.0）代码修复摘要

1. **提醒取消秒/毫秒单位错误**（确定缺陷）：快照存秒、取消接口收毫秒，旧代码把秒值直接传入导致任务身份不匹配（60 秒提醒排定传 60000→requestCode 200060/通知 ID 5060，取消却传 60→实际取消 200000/5000）。现统一在会话结束时按旧会话快照的时点×1000 取消。
2. **冷启动恢复监控**：提醒/到期广播拉起进程后幂等恢复前台服务（`recover()`/`attachService()` 也协调运行任务），锁屏处理不依赖服务启动成功。
3. **服务恢复后解锁心跳**：亮屏且无会话的恢复场景启动 2 秒心跳，覆盖"解锁不发送 USER_PRESENT"的本机路径；幂等、不重复循环、不构成重选入口。
4. **提醒迟到规则统一**：tick 兜底改用与广播/恢复相同的 `ReminderPlanner.classify()` 2 秒窗口，超窗跳过不补发。
5. **关键状态落盘**：快照、会话身份、开机归属、消费标记改 `commit()` 同步落盘（控制器单线程，非主线程），返回值区分重复/失败；会话标识先于快照落盘避免恢复后重号；普通配置项维持 `apply()`。通知请求与磁盘事务无法原子化，优先避免重复提醒。
6. **重复解锁事件**：去掉按会话年龄（3 秒）替换有效会话的逻辑，活动会话不受迟到 `USER_PRESENT` 影响。
7. **诊断页（LogActivity）**：上半屏新增后台运行健康信息（监控开关、前台服务挂载、最近服务启动/恢复原因、最近有效解锁检测、当前会话与截止、到期闹钟排定、管理员/悬浮窗/电池优化豁免/Doze/待机桶/通知渠道的实际状态；ColorOS 自启动等无可靠读取接口的项标注"需手动确认"），新增**一键诊断导出**（健康报告+完整日志合并分享）；电池优化按钮增加列表页/应用详情页两级回退。

**实测结论（审查问题 5 的答案）**：对照实验显示 ColorOS 7.1 对本应用**所有** `setExactAndAllowWhileIdle()` 闹钟统一附加数十秒级分发窗口，提醒开/关时到期闹钟窗口几乎相同（+67.5s vs +67s）——**不是提醒闹钟挤占到期的分发额度**；本机到期准点的实际保障是进程内每秒 tick 兜底（两轮实验锁屏均在 deadline+70ms 内完成）。维持现有调度方案（到期+提醒 AllowWhileIdle + tick 兜底），不换 `setAlarmClock()`；不把限流写成已确认根因。

**长期闲置（数小时/隔夜）未在本轮完成**：用户假设的"长期未打开被电池优化影响"仍属待验证；已留取证脚本（异常发生后先 `forensic` 再打开主界面）。划卡片、进程死亡、重启三类回收路径本轮均已真机验证通过。

**真机发现的两个 OEM 行为与对策（均已实现+单测）**：

1. **ColorOS 7.1 密码解锁（上滑→PIN）全程不发送 `USER_PRESENT`**——v0.1.0 依赖该广播正是 R0 故障根因。已加**解锁一致性心跳**：亮屏期间每 2 秒核对"可交互+未锁+无会话"，发现即补待选择（熄屏/建会话即停，纯内存无 IO）。10 轮回归全部由心跳路径补出。
2. **ColorOS 会合并/推迟同应用的精确闹钟与 Handler 消息**（设备静置亮屏约 45 秒后实测冻结 8-15 秒）：到期闹钟改 `setExactAndAllowWhileIdle`；提醒由每秒 tick 兜底投递"已到点未消费"的提醒（消费标记先行去重）；到期锁屏另有 tick 兜底（同一状态机路径），调度冻结期仍能完成锁屏（实测迟到 14.8s 但真实锁屏）。

### 已知边界与未验证项（如实声明）

- **长期闲置后台故障**：用户反馈"划掉后台卡片后计时/弹窗正常；上次失败可能是长期未打开被电池优化影响"。该假设**尚未证实**，属待验证：需要数小时/隔夜闲置后唤醒的取证实验（见本轮真机记录）。本轮不围绕普通划卡片增加保活机制（划卡片 ≠ 强行停止；START_STICKY 是恢复机制而非即时重启承诺；不依赖 onDestroy/onTaskRemoved 执行）。
- **同应用精确闹钟相互影响**：到期与提醒都曾用 `setExactAndAllowWhileIdle()`，平台存在按应用限制 allow-while-idle 分发频率的机制；本机是否实际触发取决于 ColorOS 配置与豁免状态，以对照实验与 `dumpsys alarm` 为准（见本轮真机记录）。
- R0 根因判断的证据边界：静态证据（v0.1.0 在 `keyguardLocked=true` 时直接丢弃 USER_PRESENT 且无复核；用户"手动打开应用就弹窗"与恢复路径行为完全吻合）指向密码解锁过渡期 keyguard 状态未稳定，但**无故障时刻的设备日志**佐证；应用已加广播入口日志，待真机复现取证确认。若真机显示 USER_PRESENT 根本未到达（ColorOS 投递问题），则需换注册方式再修。
- `ContextCompat.RECEIVER_NOT_EXPORTED` 在 API 29 的行为：AndroidX 在低于 U 的系统上不传递 not-exported 语义（注册为普通动态接收器），理论上可正常收到系统广播；本轮保留该注册方式并加入口日志，真机证据若表明漏收再调整。
- 到期后"屏幕熄灭"与"设备需要凭据解锁"是两个事实：应用分别记录 lockNow 请求、熄屏确认、keyguard 状态；设置安全密码后的完整到期-解锁链路已在 2026-10-05 用 PIN 解锁路径覆盖（多次实测）。
- 通话场景（接近黑屏/通话中锁屏）需要真实通话配合，未验证。
- ColorOS heads-up 横幅实际出现受系统/勿扰策略影响，HIGH channel 不保证必弹，需真机确认。
- ColorOS 长期杀后台存活率未验证；"故意强行停止"、卸载、主动撤销权限后不承诺自动恢复（普通应用能力边界）。
